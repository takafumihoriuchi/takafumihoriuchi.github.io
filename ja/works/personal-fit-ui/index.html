制約型デザインに基づくUIの最適化PoC

制作：堀内 貴文（Takafumi Horiuchi）

  • LinkedIn
  • GitHub

2026年8月

概要

一人ひとりの認知特性に合わせて、UIを自動で生成する試み。文献と規格から「守るべき枠」を検証できる形で書き下し、その枠の中でAIに具体を決めさせ、枠に違反していないかを機械が判定する。題材としてカーナビを選び、13体のペルソナに対してUIを生成した。

結果は、当初の見込みとは違うところに出た。生成されたUIそのものより、枠を書く過程のほうに発見があった。以下はその記録である。

なぜ「一人ひとりに合うUI」なのか

いまのUIは、マスプロダクションを前提に作られている。ひとつのUIを全ユーザーに使わせることが出発点にあり、できるだけ多くの人をカバーできるように設計される。設定で調整できるようにしてある製品も多いが、自分に合うように実際に設定を変えるユーザーは多くない。

ここで見るべきなのは、カバーされなかった側である。一部の人は、設計の時点で構造的に取りこぼされている。

これは推測ではない。米国NHTSAが定める運転中の視線に関する受入基準は、被験者24名のうち21名が満たすことを合格条件としている。規定そのものが、3名（12.5%）の不合格を制度として織り込んでいる。しかもこぼれるのは偶然のばらつきではない。自動車メーカーが規制当局へ提出した資料には、複数の異なる課題にまたがって同じ被験者が長く視線を外すこと、そしておよそ6人に1人がそうした特性を持つと見られることが記されている。

つまり「多くの人に合う」設計は、合わない人が一定割合いることを承知のうえで成立している。個別最適化されたUIの意義は、便利さの上乗せではなく、この制度的に許容された不合格者を基準の内側に入れることにある。

そして、これまで現実的でなかったのは、一人ひとりに合わせて設計し直すコストが見合わなかったからである。設計の一部にAIを組み込めるようになったことで、その前提が変わりつつある。

題材：カーナビ

検証の題材にはカーナビを選んだ。この取り組みの主題はあくまで「一人ひとりに合うUI」であり、カーナビはそれを試すための一例である。ただし題材としては都合がよかった。

カーナビは、出荷前に画一的なUIで検証を行い、多くのユーザーに適合することを確かめたうえで市場に出る。裏を返せば、適合しなかった層は、そのまま使いにくいUIを使い続けることになる。しかも運転中は安全基準が厳しく、UIが自由に取れる形は狭い。枠が厳しい領域で個別最適化が成り立つかどうかは、それ自体が問いになる。

日本では2026年現在も、多くの車両で工場出荷後にシステムアップデートが行われないカーナビが使われている。購入時のUIが、その車を手放すまでのUIになる。

制約型デザインという枠組み

私が「制約型デザイン」と呼んでいるのは、枠組みは明確に決めたうえで、その中をAIがニュアンスを捉えて柔軟に動けるようにする設計の考え方である。パラメトリックであることとは違う。パラメトリックは値を動かす仕組みだが、制約型デザインが動かすのは解の範囲である。

要点は、科学的に「数値」まで提唱されていなくても、方向や境界が提唱されているならそれを枠として採用することにある。細かい具体化はAIが行う。間違いが起きないように枠を入念に設計すること自体が、この考え方の本体である。

システムは4つの要素で構成した。

認知次元

その人を表す軸。年齢、ワーキングメモリ、妨害刺激への耐性、手指の巧緻性など。診断名を経由せず、直接測れる特性として定義する。

制約条件群

守らなければならない条件。安全基準、アクセシビリティ規格、UI設計の原則。デザイン空間を外から削る。

マッピング表

認知次元をUIのパラメータへ結ぶ、文献に基づく変換。どの特性がどのパラメータを動かすかを、根拠つきで名指しする。

デザイン空間

UIが取りうるパラメータとその定義域。文字サイズ、1画面の項目数、通知の量、語彙の平易さなど。

AIが枠の中で決める → 一人ひとりのUI

制約条件群が削り、マッピング表が位置を決めたあと、残った自由度をAIが埋める。生成されたUIが枠に違反していないかは、別のAIが二値で判定する。良し悪しの評価は人間が行う。

この流れは①枠の設計（人間）→ ②枠内での生成（AI）→ ③枠違反の検証（AI）→ ④生成物の評価（人間）→ ⑤評価を枠へ反映というループになる。④は毎回行う工程ではなく、人間が必要と判断したときの割り込みとして置いた。

PoCでわかったこと

13体のペルソナを作り、それぞれにUIを生成した。ペルソナは実在の分布ではなく、特性を意図的に振り分けた格子点である。生成物は毎回、枠に違反していないかを機械が判定してから提示する。

ほとんど変わらなかった例

認知特性が典型的な範囲にあるペルソナでは、画一UIと個別最適化UIの差はほとんど出なかった。文字サイズがわずかに大きくなっているが、並んでいる項目の数も高さも変わらない。

視覚的に変わった唯一の例

手指の巧緻性が低いペルソナでは、はっきりした違いが出た。タッチ目標を大きくした結果、1画面に置ける項目数が減り、ひとつひとつの要素が大きくなっている。文献はタッチ目標に下限を与えているが、「操作精度が低い人にはどれだけ上乗せするか」の数値は与えていない。その上乗せ量をAIがその場で決めた。

評価

目視で確かめたところ、視覚的にはっきり変わったのは、この1体だけだった。多くのペルソナにとっては、画一UI——つまり多くの人をカバーできるように設計された現行のUI——が十分に機能していた。そして変化が出た1体についても、この程度であれば既存の多くの製品が、設定の変更で実現できる。

プリセットによる個別最適化が成立することは示せた。しかし、AIでなければできないことは、ここには現れていない。

なぜこの結果になったのか

原因ははっきりしている。枠を満たす解の空間が、狭すぎた。

走行中の車載UIは、安全基準がとりわけ厳しい領域である。文字サイズは年齢から式で決まり、タッチ目標には下限があり、1画面に置ける情報の数には上限がある。これらの床と天井が順に効いた結果、AIが選べる余地はごくわずかしか残らなかった。実際に測ると、AIが決めていた項目のほとんどは、特性値から出力値への単純な対応表として書き下せてしまう。

ここは正確に言う必要がある。「AIが不要だった」のではない。その対応表の中身は、どの文献にも書かれていない。AIがしていたのは文献に無い表をその場で埋めることであり、規則に落とすなら、その表を人間が一度決めなければならない。今回わかったのは、AIが埋めた表が、人間が一度決めれば固定できる程度に小さかったということである。

枠を書く過程のほうに、発見があった

むしろ成果が出たのは、生成の前の段階だった。枠を「検証できる形」で書き下していく過程で、枠そのものの不整合が次々と見つかった。

  • ある安全基準に、「走行中に限る」という適用条件を書く場所が枠の側に無かった。そのため停車中の生成物にも課してしまい、どのUIも人間の評価まで到達できない状態になっていた。原典を読み直したところ、その基準は走行中の操作可否を判定するものだと明記されていた。
  • ふたつの規格が、同じ項目に別々の下限を与えて衝突していた。年齢によってどちらが厳しいかが入れ替わるため、どちらを採るかで結果が変わる。
  • ひとつのパラメータの定義域が、本来独立な2つの軸を1つに畳んでいた。その結果、4つの選択肢のうち3つが他の制約に弾かれ、実質1つしか選べなくなっていた。
  • どの制約がどの出力を支配するかをAIに伝えていなかったため、AIは関係のない制約を根拠に持ち出していた。伝え方を直すと、出力のばらつきが目に見えて収まった。

これらはいずれも、AIが不整合を検出し、該当する規則を名指しし、人間が判断し、枠が修正されたという経過をたどっている。制約型デザインにおけるAIの役割は、生成の段階だけにあるのではない。枠を設計する段階で、衝突を見つけて指摘することも含まれる。

つまりこのPoCが示したのは、「AIがUIを作った」ではなく「AIが枠の不整合を見つけ、枠が育った」ということだった。

これから

制約型デザインにおけるAIの役割は、枠を守ることを確約したうえで、統計的に最も確からしい解を出すこと、あるいは人間には思いつかないパターンを提示することにある。今回それが現れなかったのは、衝突が起きなかったからではなく、解の空間が狭すぎて「最も確からしい」も「思いつかない」も意味を持たなかったからである。

したがって次に問うべきは「AIは有効か」ではなく、どの程度の広さのデザイン空間から、AIならではの効果が現れるのかである。次の題材は、枠が解を一意に決めてしまわない領域から選ぶ。枠は明確に、しかし枠の中は広く——それが制約型デザインの本領が出る条件だと考えている。
